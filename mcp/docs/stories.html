Rules for every story

  1. Terms. Order currency = the currency the merchant created the order in (AED). Transaction currency = the currency the customer pays in; the scheme authorizes and clears in it. Rate = Planet’s rate from the order currency to the transaction currency, markup included. MCP transaction = a transaction where PGW converted the amount.
  2. Field names. PGW field names are camelCase. New names in these stories are proposals, except mcpBaseAmount and mcpBaseCurrency (agreed). PGW engineering can rename them. Keep the meaning.
  3. The PGW backend applies every rule, also when the screen already blocks the action.
  4. Identify the merchant by MID in every API and in all documentation.
  5. New fields in merchant APIs are additions. Do not change or remove existing fields.
  6. Times are UAE time (UTC+4). Rate validity times in Planet’s file are UTC.
  7. Amounts. Calculate with exact decimals, never floating point. Every amount is stored with the number of decimals of its currency (2 in MVP).
  8. The merchant never sees the transaction currency, the rate or an MCP flag (S7).

S1 — FE/BE – MCP configuration

Simulator: merchant set-up

Background

The PGW integration team sets merchant settings in the Backoffice: Merchants → Impersonate merchant → Payment Gateway → Configuration. The settings are stored on the MID’s PAYMENT_GATEWAY product instance, in its data object. The screen saves with the existing product instance update (PATCH /product/api/v1/productInstance/{productInstanceId}, JSON-Patch replace on data/<key>). Live and Test instances are separate.

The Gateway Settings tab already has ENABLE_MULTI_CURRENCY (isMulticurrencyEnabled, currencies). That setting lets a merchant create orders in other currencies. MCP is a different setting: it lets the customer pay in another currency. The two must stay separate.

Goal

  1. The PGW integration team can turn MCP on for a MID and choose the currencies the merchant offers.
  2. PGW holds three system lists that MCP reads: MCP currencies, the country-to-currency map and MCP order currencies.

3. Screen

  1. Add the section Dynamic multi-currency pricing in PGW configuration (tab position: PGW engineering, next to Gateway Settings).
  2. Toggle with label Dynamic multi-currency pricing and one line of text. Use a label that is clearly different from ENABLE_MULTI_CURRENCY and ENABLE_MULTI_CURRENCY_SETTLEMENT. Ship the label translated (not as a raw key).
  3. Under the toggle: a table with one row per active currency in the MCP currency list: currency code, decimals, an Offered toggle.
  4. When MCP is off, the currency table is disabled. The selected currencies stay stored.

S2 — BE – Planet rate file load and cache

Simulator: yesterday's ratesSimulator: no valid fileEnd-to-end: no valid file

Background

Planet publishes one rate file each day. The rates include the markup. PGW quotes every MCP amount from this file. No rate is fetched from Planet during a payment. Layout: Planet MAS template 194, comma-separated, with a Visa section and a Mastercard section. Each rate has its own validity window. In Planet’s sample the window is 48 hours, so two daily files overlap.

Sample (from Planet):

PFH,20260214,01
VILFH,HPLANET VISA,20260214,01
VID,1023,$,840,2,€,978,2,0.9123456,2026-02-14T00:00:00.000Z,2026-02-15T23:59:59.000Z
VID,1024,$,840,2,£,826,2,0.7890123,2026-02-14T00:00:00.000Z,2026-02-15T23:59:59.000Z
VILFT,TPLANET VISA,1804,1.7013579,2
MCLFH,HPLANET MASTERCARD,20260214,01
MCD,1025,$,840,2,€,978,2,0.9121000,2026-02-14T00:00:00.000Z,2026-02-15T23:59:59.000Z
MCLFT,TPLANET MASTERCARD,978,0.9121000,1
PFT,TXN RATES,2782,2.6134579,3

Goal

  1. PGW loads each day’s file, checks it and caches it.
  2. PGW gives HPP the rate for an order currency and a transaction currency at a point in time.
  3. When no valid rate exists, MCP is not offered, and Operations is alerted.

Story summary

Item Value
Story ID S2
Source Planet, SFTP, PGP-encrypted (as for DCC files). Until P3: Planet’s sample file loaded by PGW.
Depends on — . Live feed: P3.
Followed by S4

Requirements

1. Records (template 194)

Record Code Fields in order
Physical file header PFH date (YYYYMMDD), version
Visa section header VILFH HRateKey (HPLANET VISA), date, version
Visa detail VID rateId, baseCurr (symbol), baseCurr2 (ISO numeric), baseMinorUnit, targetCurr (symbol), targetCurr2 (ISO numeric), targetMinorUnit, rate, validFrom, validTo (ISO 8601, UTC)
Visa section trailer VILFT TRateKey (TPLANET VISA), hashTotalTargetCurrCode, hashTotalExRate, recordCount
Mastercard section MCLFH, MCD, MCLFT Same layout as Visa
Physical file trailer PFT txnRates (TXN RATES), hashTotalTargetCurrCode, hashTotalExRate, recordCount
  1. Identify currencies by the numeric codes (baseCurr2, targetCurr2). The symbol fields are for display only.
  2. rate = units of target currency for 1 unit of base currency. Converted amount = base amount × rate.
  3. Quote from the Visa section (VID). Load the Mastercard section and keep it, but do not quote from it.

2. Checks on load

Any failure: do not use the file, keep the previous cache, alert Operations with the file name and the failed check.

# Check
2.1 The file decrypts and has PFH first and PFT last.
2.2 Each section has its header and trailer.
2.3 Each section trailer recordCount = number of detail records in the section. PFT recordCount = all detail records.
2.4 hashTotalTargetCurrCode = sum of targetCurr2 of the section (PFT: all sections).
2.5 hashTotalExRate = sum of rate of the section (PFT: all sections).
2.6 Each rate is above 0. validFrom is before validTo.
2.7 A rate changes from the same pair in the previous file by no more than the change limit (configuration, e.g. 10%).
2.8 The file date and version have not been loaded before.

Worked check on the sample: Visa hashTotalTargetCurrCode 1804 = 978 + 826. hashTotalExRate 1.7013579 = 0.9123456 + 0.7890123. PFT 2782 = 978 + 826 + 978, 3 records.

3. Rate lookup

Input: order currency, transaction currency, time. Output: rate, rateId, file date and version, or “no rate”. 1. Take Visa detail records with baseCurr2 = order currency and targetCurr2 = transaction currency. 2. Keep the records where validFrom ≤ time ≤ validTo. 3. From these, use the record from the latest loaded file (highest date, then version). 4. No record: “no rate”. HPP does not offer this currency (S4).

Example: file 20261123 has GBP valid to 24-Nov 23:59:59 UTC. File 20261124 has GBP valid to 25-Nov 23:59:59 UTC. At 24-Nov 10:00 UTC both are valid. PGW uses 20261124.

4. MCP suspended

  1. When no loaded file has any valid rate, MCP is suspended for all merchants. HPP shows AED only (S4).
  2. Alert Operations when MCP becomes suspended and when it resumes.
  3. Alert Operations when no new file has loaded by a set time each day (configuration).

5. Storage

  1. Keep every received file and its load result (loaded / failed, with the check) for audit.
  2. The cache is shared by all PGW instances that serve HPP.

Acceptance criteria

  1. Load Planet’s sample file: loaded. Lookup USD → GBP at 2026-02-14T12:00Z returns 0.7890123, rateId 1024.
  2. Lookup USD → EUR returns the Visa rate 0.9123456, not the Mastercard rate 0.9121000.
  3. Change VILFT record count to 3: file fails (2.3), previous cache kept, Operations alerted.
  4. Change one rate by 50% against the previous file: file fails (2.7).
  5. Two valid files: the later file’s rate is returned.
  6. Lookup after validTo of every file: “no rate”. MCP suspended, Operations alerted.
  7. Load the same file twice: second load rejected (2.8).

S3 — BE – Customer country from IP (MaxMind)

Simulator: no country foundSimulator: customer in the UAE

Background

MCP proposes a currency from the customer’s location. PGW holds the MaxMind GeoIP2 downloadable database (approved 23-Nov-2026) and looks up the customer’s IP address in it. No external call is made during the payment session.

Goal

PGW returns the customer’s country for an IP address, fast enough to run before HPP shows the amount.

Story summary

Item Value
Story ID S3
Source MaxMind GeoIP2 database, hosted by PGW
Depends on P2
Followed by S4
Out of scope VPN and proxy detection (accepted risk)

Requirements

  1. Input: the customer’s public IP address (IPv4 or IPv6) as received by HPP, after any Geidea load balancer.
  2. Output: ISO 3166 alpha-2 country code, or “not found”.
  3. Refresh the database as MaxMind publishes updates. Keep the current database in use until the new one loads correctly.
  4. Lookup error, empty result or a private address: “not found”.
  5. Alert Operations when the database has not refreshed within the expected period (configuration).
  6. Store the IP address used and the country found on the HPP session, for support.

Acceptance criteria

  1. A known UK test address returns GB.
  2. A private address (e.g. 10.0.0.1) returns “not found”.
  3. The lookup works for IPv4 and IPv6.
  4. A failed database refresh keeps the previous database in use and raises an alert.

S4 — FE/BE – HPP currency offer and selection

Simulator: GBP offeredSimulator: rounding upSimulator: TabbyEnd-to-end view

Background

The customer pays on Geidea HPP. HPP opens from Create Session (POST /payment-intent/api/v2/direct/session), from an SDK that shows Geidea HPP, or from Pay-by-Link. MCP is decided when HPP loads. Flows that never show HPP (Direct API with card details from the merchant, recurring and merchant-initiated payments) are never MCP.

MCP is offered strictly on location. When PGW does not propose a currency, HPP is the same as today: AED only, no selector.

Goal

  1. When the customer’s location gives a currency the merchant offers, HPP shows the amount in that currency, the AED amount and the rate.
  2. The customer can switch between the offered currencies and AED.
  3. The quote stays fixed for the session.

Story summary

Item Value
Story ID S4
Reads isDynamicMcpEnabled, dynamicMcpCurrencies (S1), system lists (S1), rate lookup (S2), country (S3)
Session fields written mcpCountry, mcpProposedCurrency, mcpQuotes[], isMcpOffered
Depends on S1, S2, S3
Followed by S5

Requirements

1. Decide the offer (when HPP first loads)

PGW runs these checks in order. The first “no” stops the check: MCP is not offered and HPP shows AED only, with no selector.

# Check Source
1.1 The order currency is in the MCP order currencies list (AED). S1
1.2 paymentOperation = Pay. Session
1.3 isDynamicMcpEnabled = true for the MID and instance. S1
1.4 MCP is not suspended (a valid rate file exists). S2
1.5 The customer’s IP gives a country. S3
1.6 The country maps to an active currency, other than the order currency. S1
1.7 The currency is in dynamicMcpCurrencies of the MID. S1
1.8 The rate lookup returns a rate for order currency → that currency. S2

All “yes”: the mapped currency is the proposed currency. Set isMcpOffered = true.

Why 1.6 excludes the order currency. A customer in the UAE maps to AED. Nothing is converted, so MCP is not offered and HPP shows no selector.

2. Quotes (fixed for the session)

When MCP is offered, build one quote for each currency in dynamicMcpCurrencies that has a rate (S2 section 3), at the time HPP first loads:

Quote field Value
currency Transaction currency
amount Order amount × rate, rounded up to the currency’s decimals
rate From S2 (7 decimals)
rateId, rateFileDate, rateFileVersion From S2
  1. Store the quotes on the session (mcpQuotes[]). A reload of the same session uses the stored quotes. A newer rate file does not change them.
  2. Never recalculate an amount from a newer rate during the session.

Rounding up, examples (rate AED → GBP 0.2137000):

Order amount (AED) × rate Quote (GBP)
100.00 21.3700000 21.37
99.99 21.3678630 21.37
0.01 0.0021370 0.01

3. Display

# Element Content
3.1 Total The quote amount and currency of the selected currency (first: the proposed currency), e.g. “GBP 21.37”.
3.2 Order amount “Order amount AED 100.00”. Shown only when the selected currency is not AED.
3.3 Rate “Exchange rate 1 AED = 0.2137 GBP”. The rate as in the file, trailing zeros removed. Shown only when the selected currency is not AED.
3.4 Currency selector Paying in: AED and every currency with a quote. Shown only when MCP is offered.
3.5 Wallet buttons Apple Pay, Google Pay, Samsung Pay built with the selected currency and amount. Shown below 3.1 to 3.4.
3.6 Tabby, Tamara Selectable only when the selected currency is AED. Show “Available in AED only” under them when MCP is offered.
3.7 Pay button “Pay GBP 21.37” (selected currency and amount).
  1. Changing the selector updates 3.1 to 3.7 from the stored quotes. AED shows the order amount.
  2. When the customer selects a non-AED currency while Tabby or Tamara is selected, select card.
  3. No further disclosure text about the conversion.

4. Backend checks when HPP submits the payment

# Check On failure
4.1 The submitted currency is AED or a currency in mcpQuotes[]. Reject. Message: “Currency not available. Reload the page.”
4.2 The submitted amount equals the stored quote (or the order amount for AED). Reject. Same message.
4.3 Tabby or Tamara only with AED. Reject. Message: “This payment method is available in AED only.”

PGW engineering sets the error codes.

Acceptance criteria

  1. MID with MCP on, GBP offered. Customer IP in the UK, order AED 100.00: HPP shows GBP 21.37, AED 100.00, “1 AED = 0.2137 GBP” and the selector. isMcpOffered = true.
  2. Same customer selects AED: total AED 100.00, no order amount line, no rate line. Tabby is selectable.
  3. Customer in the UAE: AED only, no selector. isMcpOffered = false.
  4. Customer in India, INR not offered by the MID: AED only, no selector.
  5. Customer in Japan: AED only, no selector (Phase 2 country).
  6. No country found: AED only, no selector.
  7. MCP suspended (no valid rate file): AED only, no selector.
  8. Order in USD, or paymentOperation = PreAuthorize: no MCP.
  9. Order AED 99.99, customer in the UK: GBP 21.37.
  10. A new rate file loads while the page is open, then the customer reloads: the amount does not change.
  11. A tampered submit with GBP 20.00: rejected (4.2).
  12. Pay-by-Link opened from the UK: same behaviour as 1.

S5 — BE – MCP payment and transaction record

Simulator: Apple PaySimulator: wallet mismatchEnd-to-end view

Background

S4 gives a fixed quote. When the customer pays in a non-AED currency, PGW authorizes in that currency through MPGS or CyberSource, as for any non-AED payment. PGW must keep two views of the payment: the order view in AED, which the merchant and APEX use, and the transaction view in the paid currency, which the scheme uses.

Goal

  1. PGW authorizes in the currency the customer chose, at the quoted amount.
  2. PGW stores both views and the rate on the transaction.
  3. Order totals stay in the order currency.

Story summary

Item Value
Story ID S5
Geidea endpoints HPP pay flow; POST /pgw/api/v2/direct/pay, POST /pgw/api/v2/direct/pay/token

Followed by S6, S7, S8, S9

Requirements

1. Authorization

  1. Send the selected currency and the quote amount to MPGS or CyberSource, as for any non-AED payment. No new processor fields. MPGS and CyberSource are set up for the full ISO currency list.
  2. AED selected: process as today.
  3. A declined payment can be retried in the same session with the same quote.

2. Wallet check

  1. For Apple Pay, Google Pay and Samsung Pay, compare the amount and currency in the wallet payment data with the quote of the selected currency.
  2. Different: reject the payment. Message: “Payment amount does not match. Try again.” Do not send it to the processor.

3. Fields

Why mcpBaseAmount is filled for every transaction. Order totals, the merchant outputs (S7) and the federation (S8) read one field for all transactions.

Why the name is not originalAmount. PGW already uses originalAmount for the amount before fees.

4. Order totals

  1. Compute every order total (paid, refunded, remaining to refund) from mcpBaseAmount.
  2. Never add amount values of transactions in different currencies.

Example: purchase mcpBaseAmount 100.00, refund mcpBaseAmount 60.00 → refunded AED 60.00, remaining AED 40.00.

5. Confirmation

  1. The HPP confirmation shows the paid amount and the AED order amount: “GBP 21.37 (AED 100.00)”.
  2. Pay-by-Link: PGW sends the customer an email receipt when the customer has an email address. For an MCP payment it shows the same: “GBP 21.37 (AED 100.00)”.
  3. AED payments: as today.

Acceptance criteria

  1. Pay GBP 21.37 on an AED 100.00 order by card: processor receives GBP 21.37. Transaction: amount 21.37, currency GBP, isMcp true, mcpBaseAmount 100.00, mcpBaseCurrency AED, mcpRate 0.2137000.
  2. Pay in AED on an MCP-offered session: isMcp false, mcpBaseAmount 100.00 AED. isMcpOffered true on the order.
  3. Apple Pay with GBP 21.37 in the token: approved. Token with GBP 21.36: rejected before the processor.
  4. Decline, then retry in the same session: same quote and rate.
  5. Order inquiry totals are in AED.
  6. Confirmation shows “GBP 21.37 (AED 100.00)”.
  7. Pay-by-Link paid in GBP by a customer with an email address: the email receipt shows “GBP 21.37 (AED 100.00)”.

S6 — BE – MCP refunds

End-to-end: refunds AED 60 + 40

Background

The merchant refunds in AED with the existing refund API (refund v2, signed with timestamp + merchantPublicKey + refundAmount + orderId). For an MCP transaction the customer paid in another currency, so the refund must go to the processor in that currency. PGW converts it at the rate stored on the original transaction. Converting each partial refund on its own can leave a cent unrefunded. The last-cent rule closes the gap at PGW.

Goal

  1. A refund of an MCP transaction is sent in the transaction currency at the stored rate.
  2. The refunds of a transaction never total more or less than the amount paid, in both currencies.
  3. A refund too small to convert is rejected, except the final one.

Story summary

Item Value
Story ID S6
Geidea endpoint Existing refund v2. refundAmount in the order currency. No new request fields.
Fields written Refund transaction: amount, currency, isMcp, mcpBaseAmount, mcpBaseCurrency, mcpRate, mcpRateId, mcpRateFileDate, mcpRateFileVersion
Depends on S5
Out of scope Manual refunds by FinOps through Postilion. Void (as today).

Requirements

1. Checks

# Check Message
1.1 Existing refund checks, on AED: refundAmount ≤ AED paid − AED already refunded (from mcpBaseAmount). Existing message
1.2 The refund converts to at least one minor unit of the transaction currency (section 2), unless it is the final refund. Refund amount is below the minimum refundable amount.

The message for 1.2 does not show the transaction currency.

2. Conversion (original purchase isMcp = true)

  1. Final refund: AED already refunded + refundAmount = AED paid. Refund amount in transaction currency = purchase amount − all earlier refunds’ amount.
  2. Other refunds: refundAmount × purchase mcpRate, rounded down to the currency’s decimals.
  3. Use the purchase mcpRate. Never look up a new rate.
  4. Send the refund to the processor in the transaction currency.
  5. Store on the refund transaction: amount and currency = converted amount and transaction currency; mcpBaseAmount = refundAmount; mcpBaseCurrency = AED; isMcp = true; rate fields copied from the purchase.

Original purchase isMcp = false: refund as today.

Why round down. Each earlier refund then stays at or below its exact value, so the final refund is never negative.

Acceptance criteria

  2. Refund AED 33.33, 33.33, 33.34: GBP 7.12, 7.12, 7.13.
  3. Full refund AED 100.00 in one call: GBP 21.37.
  4. Refund AED 0.04 as a non-final refund: rejected (1.2). Message does not name GBP.
  5. Refund AED 0.04 as the final refund: accepted, GBP = remaining amount.
  6. A new rate file has loaded since the purchase: refund still uses 0.2137000.
  7. Refund AED 100.01: rejected (1.1).
