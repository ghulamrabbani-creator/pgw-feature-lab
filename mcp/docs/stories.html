Rules for every story

  1. Terms. Order currency = the currency the merchant created the order in (AED). Transaction currency = the currency the customer pays in; the scheme authorizes and clears in it. Rate = Planet’s rate from the order currency to the transaction currency, markup included. MCP transaction = a transaction where PGW converted the amount.
  2. Field names. PGW field names are camelCase. New names in these stories are proposals, except mcpBaseAmount and mcpBaseCurrency (agreed). PGW engineering can rename them. Keep the meaning.
  3. The PGW backend applies every rule, also when the screen already blocks the action.
  4. Identify the merchant by MID in every API and in all documentation.
  5. New fields in merchant APIs are additions. Do not change or remove existing fields.
  6. Times are UAE time (UTC+4). Rate validity times in Planet’s file are UTC.
  7. Amounts. Calculate with exact decimals, never floating point. Every amount is stored with the number of decimals of its currency (2 in MVP).
  8. The merchant never sees the transaction currency, the rate or an MCP flag (S7).

S1 — FE/BE – MCP configuration

Simulator: merchant set-up

Background

The PGW integration team sets merchant settings in PGW Configuration. The settings are stored on the MID’s PAYMENT_GATEWAY product instance, in its data object. The screen saves with the existing product instance update (PATCH /product/api/v1/productInstance/{productInstanceId}, JSON-Patch replace on data/<key>). Live and Test instances are separate.

The Gateway Settings tab already has ENABLE_MULTI_CURRENCY (isMulticurrencyEnabled, currencies). That setting lets a merchant create orders in other currencies. MCP is a different setting: it lets the customer pay in another currency. The two must stay separate.

Goal

  1. The PGW integration team can turn MCP on for a MID and choose the currencies the merchant offers.
  2. PGW holds three system lists that MCP reads: MCP currencies, the country-to-currency map and MCP order currencies.

Depends on — . Before a MID is set up: P1.

Out of scope Markup (held at Planet). Merchant portal login (no access).

Requirements

1. Settings in data (Live and Test separately)

Field Type Default Values
isDynamicMcpEnabled Boolean false true = MCP on for this MID
dynamicMcpCurrencies Array of String [] ISO 4217 alpha codes, each from the MCP currency list (section 2)
  1. Existing MIDs: add both fields with the defaults.
  2. The existing product instance search returns the fields. The existing update accepts them.

2. System lists (configuration, not per MID)

Store as configuration. Do not write the values in code.

List Content Initial value
MCP currency list Currencies MCP can offer: currency code, numeric code, decimals, active 2-decimal currencies that APEX supports and Planet’s file carries. For build and test: GBP, EUR, INR, USD, SAR. Production list from P6.
Country-to-currency map ISO 3166 alpha-2 country → currency code, active flag From the Feature Brief: GB → GBP, US → USD, SA → SAR, QA → QAR, IN → INR, CN → CNY, RU → RUB, CH → CHF, AU → AUD, CA → CAD, SG → SGD, Eurozone countries → EUR. JP, KW, BH, OM inactive (Phase 2).
MCP order currencies Order currencies MCP applies to AED

3. Screen

  1. Add the section Dynamic multi-currency pricing in PGW Configuration (tab position: PGW engineering, next to Gateway Settings).
  2. Toggle with label Dynamic multi-currency pricing and one line of text. Use a label that is clearly different from ENABLE_MULTI_CURRENCY and ENABLE_MULTI_CURRENCY_SETTLEMENT. Ship the label translated (not as a raw key).
  3. Under the toggle: a table with one row per active currency in the MCP currency list: currency code, decimals, an Offered toggle.
  4. When MCP is off, the currency table is disabled. The selected currencies stay stored.
  5. A note under the table: “No markup is set here. Markup is held at Planet and is included in the rates.”
  6. Discard Changes and Save changes work as on the other tabs.

4. Checks on Save changes

# Check Message
4.1 MCP on → at least one currency offered. Select at least one currency.
4.2 Each currency is in the MCP currency list and active. {code} is not available for MCP.
  1. Any failure: do not save. Show the message and the banner “Changes not saved. Fix the highlighted fields.”
  2. No failure: save the changed fields.

5. Effect of a saved change

Change Effect
MCP turned on Applies to HPP sessions opened after the save.
MCP turned off, or a currency removed New HPP sessions do not offer it. Payments already made and their refunds keep their stored rate (S6).

Acceptance criteria

  1. New MID: MCP off, no currencies.
  2. Turn MCP on, save with no currency: message 4.1.
  3. Turn MCP on, offer GBP and EUR, save, reload: values shown.
  4. Turn MCP off, save, reload: MCP off, GBP and EUR still selected and disabled.
  5. Change on Test: Live does not change.
  6. Remove INR from the MCP currency list in configuration: INR is not shown on the screen and a save with INR is rejected (4.2).

S2 — BE – Planet rate file: fetch, parse and store

Simulator: yesterday's ratesSimulator: no valid fileEnd-to-end: no valid file

Background

Planet publishes one rate file each day. The rates include the markup. This story only brings the file into PGW: fetch it, decrypt it, parse it and store the rates in a table. S4 reads the table when HPP loads.

Layout: Planet MAS template 194, comma-separated, with a Visa section and a Mastercard section. Planet’s sample (USD base; Geidea’s file will have AED as the base currency):

PFH,20260214,01
VILFH,HPLANET VISA,20260214,01
VID,1023,$,840,2,€,978,2,0.9123456,2026-02-14T00:00:00.000Z,2026-02-15T23:59:59.000Z
VID,1024,$,840,2,£,826,2,0.7890123,2026-02-14T00:00:00.000Z,2026-02-15T23:59:59.000Z
VILFT,TPLANET VISA,1804,1.7013579,2
MCLFH,HPLANET MASTERCARD,20260214,01
MCD,1025,$,840,2,€,978,2,0.9121000,2026-02-14T00:00:00.000Z,2026-02-15T23:59:59.000Z
MCLFT,TPLANET MASTERCARD,978,0.9121000,1
PFT,TXN RATES,2782,2.6134579,3

Goal

Each day’s rates are in the PGW rate table, one row per rate.

Story summary

Item Value
Story ID S2
Source Planet, SFTP, once a day
Table written mcp_rate (name is a proposal)
Depends on P3 for the live feed. Until then, load Planet’s sample file.
Followed by S4
Out of scope Rate lookup and MCP suspension (S4). Refunds use the rate stored on the transaction, not this table (S6).

Requirements

1. Fetch

  1. Collect the file from Planet’s SFTP folder once a day, after Planet’s publishing time (P3). Retry until a set time (configuration). Alert Operations when no file has arrived by then.
  2. Encryption. Planet is to confirm whether the file is PGP-encrypted (P3). If it is: Geidea creates a PGP key pair for PGW and gives Planet the public key. Planet encrypts with it. PGW decrypts with the private key. Keep the private key in PGW’s secrets store, never in code or configuration files.
  3. Keep the received file as it is, for audit.

2. Basic checks

# Check
2.1 The first record is PFH and the last record is PFT.
2.2 PFT recordCount = the number of detail records (VID + MCD).
2.3 The file date and version have not been loaded before.

Any failure: do not load the file. Keep the rows already in the table. Alert Operations with the file name and the failed check.

Why only basic checks. Planet guarantees its rates and pays any difference. The checks only make sure the whole file arrived and is not loaded twice.

3. Parse: what to keep and what to drop

Records

Record Code Action
Physical file header PFH Take date and version onto every row. Do not store the record.
Section header VILFH, MCLFH Take the card network (VISA or MASTERCARD) onto the rows of the section. Do not store the record.
Detail record VID, MCD Store one row each (section 4).
Section trailer VILFT, MCLFT Drop.
Physical file trailer PFT Use for check 2.2. Do not store.

Fields of a detail record (in file order)

# Field Keep or drop Reason
1 rateId Keep Planet’s ID of the rate. Stored on each MCP transaction.
2 baseCurr Drop Currency symbol (e.g. $). Display only.
3 baseCurr2 Keep ISO numeric code of the base (order) currency.
4 baseMinorUnit Keep Decimals of the base currency.
5 targetCurr Drop Currency symbol. Display only.
6 targetCurr2 Keep ISO numeric code of the target (transaction) currency.
7 targetMinorUnit Keep Decimals of the target currency.
8 rate Keep The rate, markup included.
9 validFrom Keep Start of validity (UTC).
10 validTo Keep End of validity (UTC).

4. Table mcp_rate

One row per detail record. Example: the Geidea file of 24-Nov-2026, Visa row for GBP.

Column Type Value Example
rateFileDate Date PFH date 2026-11-24
rateFileVersion String PFH version 01
cardNetwork String VISA for VID rows, MASTERCARD for MCD rows VISA
rateId String rateId 2001
baseCurrency String (3) ISO alpha code of baseCurr2 AED (from 784)
baseMinorUnit Integer baseMinorUnit 2
targetCurrency String (3) ISO alpha code of targetCurr2 GBP (from 826)
targetMinorUnit Integer targetMinorUnit 2
rate Decimal (7 decimals) rate, exactly as in the file. Meaning: 1 unit of baseCurrency = rate units of targetCurrency, markup included. 0.2137000 (1 AED = 0.2137 GBP)
validFrom Timestamp (UTC) validFrom 2026-11-24 00:00:00
validTo Timestamp (UTC) validTo 2026-11-25 23:59:59
loadedAt Timestamp When PGW loaded the file 2026-11-24 04:10 UAE
  1. Store both sections. S4 quotes from VISA rows only. Keeping the Mastercard rows lets Geidea switch later by configuration.
  2. Do not delete the rows of earlier files. Each daily file overlaps the next (48-hour validity in Planet’s sample). Rows older than the retention period (configuration) can be removed.

Acceptance criteria

  1. Load Planet’s sample file: 3 rows. Row rateId 1024: VISA, USD → GBP, 0.7890123, valid 14-Feb 00:00 to 15-Feb 23:59:59 UTC.
  2. No currency symbols are stored.
  3. Change the PFT record count to 4: the file is not loaded (2.2). Operations is alerted. Earlier rows stay.
  4. Load the same file twice: the second load is rejected (2.3).
  5. When P3 confirms PGP: an encrypted file is decrypted with the private key and loaded.

S3 — BE – MaxMind database: fetch, parse and store

Simulator: no country foundSimulator: customer in the UAE

Background

MCP proposes a currency from the customer’s country. PGW finds the country from the customer’s IP address with the MaxMind GeoIP2 database (approved 23-Nov-2026). MaxMind publishes the database as a zip file of CSV files. This story only brings it into PGW: fetch it, parse it and store it in a table. S4 looks up the IP address when HPP loads.

Goal

The latest MaxMind data is in the PGW geolocation table.

Story summary

Item Value
Story ID S3
Source MaxMind download permalink from the MaxMind account portal, for example https://download.maxmind.com/geoip/databases/GeoIP2-Country-CSV/download?suffix=zip. Basic authentication with the MaxMind account ID and licence key.
Table written mcp_geoip_network (name is a proposal)
Depends on P2
Followed by S4
Out of scope IP lookup (S4). VPN and proxy detection (accepted risk).

Requirements

1. Fetch

  1. Each day, check the release date with a HEAD request on the permalink (MaxMind’s recommended method). Download only when the release is newer than the one loaded.
  2. Keep the account ID and licence key in PGW’s secrets store.
  3. Keep the downloaded zip for audit. The zip name carries the release date: GeoIP2-Country-CSV_YYYYMMDD.zip.
  4. Download or load failure: keep the current data. Alert Operations.

2. Files to use

Column Keep or drop Reason

4. Table mcp_geoip_network

One row per network. The join columns are not stored.

Column Type Value Example (illustrative)
ipVersion Integer 4 or 6, from the file 4
networkStart IP address First address of network 81.2.69.0
networkEnd IP address Last address of network 81.2.69.255

  1. Load a new release completely before PGW uses it. Until then, S4 uses the previous release.
  2. Keep only the release in use and the one before it.

Acceptance criteria

  1. Load a release: one row per network in the two blocks files. No dropped column is stored.
  2. A network with an empty geoname_id gets the country of registered_country_geoname_id.
  3. The HEAD check finds no newer release: nothing is downloaded.
  4. A failed download keeps the current data and alerts Operations.
  5. While a new release loads, lookups still use the previous release.

S4 — FE/BE – HPP currency offer and selection

Simulator: GBP offeredSimulator: rounding upSimulator: TabbyEnd-to-end view

Background

The customer pays on Geidea HPP. HPP opens from Create Session (POST /payment-intent/api/v2/direct/session), from an SDK that shows Geidea HPP, or from Pay-by-Link. MCP is decided when HPP loads. Flows that never show HPP (Direct API with card details from the merchant, recurring and merchant-initiated payments) are never MCP.

MCP is offered strictly on location. When PGW does not propose a currency, HPP is the same as today: AED only, no selector.

Goal

  1. When the customer’s location gives a currency the merchant offers, HPP shows the amount in that currency, the AED amount and the rate.
  2. The customer can switch between the offered currencies and AED.
  3. The quote stays fixed for the session.

Story summary

Item Value
Story ID S4
Reads isDynamicMcpEnabled, dynamicMcpCurrencies (S1), system lists (S1), mcp_rate (S2), mcp_geoip_network (S3)
Session fields written mcpCountry, mcpProposedCurrency, mcpQuotes[], isMcpOffered
Depends on S1, S2, S3
Followed by S5

Flow

The classic MCP path: a UK customer pays an AED 100.00 order in GBP.

MCP payment on HPP

Requirements

1. Decide the offer (when HPP first loads)

PGW runs these checks in order. The first “no” stops the check: MCP is not offered and HPP shows AED only, with no selector.

# Check Source
1.1 The order currency is in the MCP order currencies list (AED). S1
1.2 paymentOperation = Pay. Session
1.3 isDynamicMcpEnabled = true for the MID and instance. S1
1.4 MCP is not suspended (section 2). S2
1.5 The country lookup (section 2) returns a country. S3
1.6 The country maps to an active currency, other than the order currency. S1
1.7 The currency is in dynamicMcpCurrencies of the MID. S1
1.8 The rate lookup (section 2) returns a rate for order currency → that currency. S2

All “yes”: the mapped currency is the proposed currency. Set isMcpOffered = true.

Why 1.6 excludes the order currency. A customer in the UAE maps to AED. Nothing is converted, so MCP is not offered and HPP shows no selector.

2. Lookups

Country lookup (table from S3) 1. Take the customer’s public IP address as received by HPP, after any Geidea load balancer. 2. Find the row of mcp_geoip_network with the same ipVersion where networkStart ≤ IP ≤ networkEnd. Result: countryIsoCode. 3. No row, an empty countryIsoCode or a private address (e.g. 10.0.0.1): no country. 4. Store the IP address and the country on the session, for support.

Rate lookup (table from S2) 1. Take the rows of mcp_rate with cardNetwork = VISA, baseCurrency = order currency, targetCurrency = the currency, and validFrom ≤ now ≤ validTo. 2. Use the row of the latest file (highest rateFileDate, then rateFileVersion). 3. No row: no rate. The currency is not offered.

Example: file 20261123 has GBP valid to 24-Nov 23:59:59 UTC. File 20261124 has GBP valid to 25-Nov 23:59:59 UTC. At 24-Nov 10:00 UTC both are valid. PGW uses 20261124.

MCP suspended 1. When mcp_rate has no VISA row valid now, MCP is suspended for all merchants. Every HPP shows AED only. 2. Alert Operations when MCP becomes suspended and when it resumes.

3. Quotes (fixed for the session)

Calculator: rounding up

When MCP is offered, build one quote for each currency in dynamicMcpCurrencies that has a rate (section 2), at the time HPP first loads:

Quote field Value
currency Transaction currency
amount Order amount × rate, rounded up to the currency’s decimals
rate From the rate lookup (7 decimals)
rateId, rateFileDate, rateFileVersion From the rate lookup
  1. Store the quotes on the session (mcpQuotes[]). A reload of the same session uses the stored quotes. A newer rate file does not change them.
  2. Never recalculate an amount from a newer rate during the session.

Rounding up, examples (rate AED → GBP 0.2137000):

Order amount (AED) × rate Quote (GBP)
100.00 21.3700000 21.37
99.99 21.3678630 21.37
0.01 0.0021370 0.01

4. Display

# Element Content
4.1 Total The quote amount and currency of the selected currency (first: the proposed currency), e.g. “GBP 21.37”.
4.2 Order amount “Order amount AED 100.00”. Shown only when the selected currency is not AED.
4.3 Rate “Exchange rate 1 AED = 0.2137 GBP”. The rate as in the file, trailing zeros removed. Shown only when the selected currency is not AED.
4.4 Currency selector Paying in: AED and every currency with a quote. Shown only when MCP is offered.
4.5 Wallet buttons Apple Pay, Google Pay, Samsung Pay built with the selected currency and amount. Shown below 4.1 to 4.4.
4.6 Tabby, Tamara Selectable only when the selected currency is AED. Show “Available in AED only” under them when MCP is offered.
4.7 Pay button “Pay GBP 21.37” (selected currency and amount).
  1. Changing the selector updates 4.1 to 4.7 from the stored quotes. AED shows the order amount.
  2. When the customer selects a non-AED currency while Tabby or Tamara is selected, select card.
  3. No further disclosure text about the conversion.

5. Backend checks when HPP submits the payment

# Check On failure
5.1 The submitted currency is AED or a currency in mcpQuotes[]. Reject. Message: “Currency not available. Reload the page.”
5.2 The submitted amount equals the stored quote (or the order amount for AED). Reject. Same message.
5.3 Tabby or Tamara only with AED. Reject. Message: “This payment method is available in AED only.”

PGW engineering sets the error codes.

Acceptance criteria

  1. MID with MCP on, GBP offered. Customer IP in the UK, order AED 100.00: HPP shows GBP 21.37, AED 100.00, “1 AED = 0.2137 GBP” and the selector. isMcpOffered = true.
  2. Same customer selects AED: total AED 100.00, no order amount line, no rate line. Tabby is selectable.
  3. Customer in the UAE: AED only, no selector. isMcpOffered = false.
  4. Customer in India, INR not offered by the MID: AED only, no selector.
  5. Customer in Japan: AED only, no selector (Phase 2 country).
  6. No country found: AED only, no selector.
  7. MCP suspended (no valid rate file): AED only, no selector.
  8. Order in USD, or paymentOperation = PreAuthorize: no MCP.
  9. Order AED 99.99, customer in the UK: GBP 21.37.
  10. A new rate file loads while the page is open, then the customer reloads: the amount does not change.
  11. Two valid rate files: the quote uses the later file.
  12. No VISA rate valid now: MCP suspended, AED only, Operations alerted.
  13. A customer IP with no matching network: no country, AED only.
  14. A tampered submit with GBP 20.00: rejected (5.2).
  15. Pay-by-Link opened from the UK: same behaviour as 1.

S5 — BE – MCP payment and transaction record

Order model: after the purchaseSimulator: Apple PaySimulator: wallet mismatchEnd-to-end view

Background

S4 gives a fixed quote. When the customer pays in a non-AED currency, PGW authorizes in that currency through MPGS or CyberSource, as for any non-AED payment. PGW must keep two views of the payment: the order view in AED, which the merchant and APEX use, and the transaction view in the paid currency, which the scheme uses.

Goal

  1. PGW authorizes in the currency the customer chose, at the quoted amount.
  2. PGW stores both views and the rate on the transaction.
  3. Order totals stay in the order currency.

Story summary

Item Value
Story ID S5
Geidea endpoints HPP pay flow; POST /pgw/api/v2/direct/pay, POST /pgw/api/v2/direct/pay/token
Fields written Order: isMcpOffered. Transaction: isMcp, mcpBaseAmount, mcpBaseCurrency, mcpRate, mcpRateId, mcpRateFileDate, mcpRateFileVersion
Depends on S4
Followed by S6, S7, S8, S9

Requirements

1. Authorization

  1. Send the selected currency and the quote amount to MPGS or CyberSource, as for any non-AED payment. No new processor fields. MPGS and CyberSource are set up for the full ISO currency list.
  2. AED selected: process as today.
  3. A declined payment can be retried in the same session with the same quote.

2. Wallet check

  1. For Apple Pay, Google Pay and Samsung Pay, compare the amount and currency in the wallet payment data with the quote of the selected currency.
  2. Different: reject the payment. Message: “Payment amount does not match. Try again.” Do not send it to the processor.

4. Order totals

  1. Compute every order total (paid, refunded, remaining to refund) from mcpBaseAmount.
  2. Never add amount values of transactions in different currencies.

S6 — BE – MCP refunds

Order model: refunds 60 + 40Calculator: refunds AED 60 + 40End-to-end: refunds AED 60 + 40

Background

The merchant refunds in AED with the existing refund API (refund v2, signed with timestamp + merchantPublicKey + refundAmount + orderId). For an MCP transaction the customer paid in another currency, so the refund must go to the processor in that currency. PGW converts it at the rate stored on the original transaction. Converting each partial refund on its own can leave a cent unrefunded. The last-cent rule closes the gap at PGW.

Goal

  1. A refund of an MCP transaction is sent in the transaction currency at the stored rate.
  2. The refunds of a transaction never total more or less than the amount paid, in both currencies.

Why no MCP-specific minimum. The existing minimum of AED 0.10 always converts to at least one minor unit in every MVP currency, because each of them has a rate of 0.1 or more per AED. Example: AED 0.10 × 0.2137000 = GBP 0.021370 → GBP 0.02.

2. Conversion (original purchase isMcp = true)

Calculator: why round down
  1. Final refund: AED already refunded + refundAmount = AED paid. Refund amount in transaction currency = purchase amount − all earlier refunds’ amount.
  2. Other refunds: refundAmount × purchase mcpRate, rounded down to the currency’s decimals.
  3. Use the purchase mcpRate. Never look up a new rate.
  4. Send the refund to the processor in the transaction currency.
  5. Store on the refund transaction: amount and currency = converted amount and transaction currency; mcpBaseAmount = refundAmount; mcpBaseCurrency = AED; isMcp = true; rate fields copied from the purchase.

Original purchase isMcp = false: refund as today.

Why round down. Each earlier refund then stays at or below its exact value, so the final refund is never negative.
