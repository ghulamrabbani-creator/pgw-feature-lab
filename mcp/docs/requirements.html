1. Objective

A customer on Geidea’s hosted payment page (HPP) is offered the price in the currency of the country they are in, and can pay in that currency. The merchant keeps pricing, reporting and settlement in its own order currency (AED). Geidea earns an FX markup on every converted payment. Planet Payment provides the rates and holds the markup, as it does for POS DCC today.

This document sets out what each Geidea system and team must deliver. It is organized by system. The PGW dev stories (MCP – PGW Dev Stories) give the PGW requirements at build level.

2. How the merchant experiences this

Nothing changes for the merchant. It creates orders in AED, sees AED in every API response, webhook, report and portal screen, and is settled in its settlement currency as today. The merchant is not told that the customer paid in another currency. This is the design boundary that every requirement below respects.

3. How the customer experiences this

HPP simulator
  1. The customer opens the payment page from the merchant’s site, an SDK that shows Geidea HPP, or a Pay-by-Link.
  2. PGW finds the customer’s country from the IP address. If the merchant offers that country’s currency, the HPP shows the total in that currency, the order amount in AED and the exchange rate.
  3. The customer can keep the proposed currency, choose another currency the merchant offers, or go back to AED.
  4. Card, Apple Pay, Google Pay and Samsung Pay are paid in the chosen currency. Tabby and Tamara are available in AED only.
  5. The confirmation shows the amount paid and the AED order amount.

When PGW does not propose a currency (location not found, the country’s currency is not offered, or the customer is in the UAE), the HPP shows AED only, with no currency selector, as today.

4. The three currencies

End-to-end view
Currency What it is Who sees it
Order currency AED. What the merchant priced the order in. Merchant, Merchant Portal, merchant reports. APEX main amount and currency fields.
Transaction currency The currency the customer pays in. The scheme authorizes and clears in it. APEX calls it the cardholder currency. Customer, PGW, MPGS/CyberSource, Postilion, scheme, Planet. APEX cardholder fields (internal). Never the merchant.
Settlement currency What the merchant is paid out in. Not changed by MCP. Merchant (as today).

Worked example used throughout: order AED 100.00. The customer is in the UK and pays GBP 21.37 at Planet’s rate AED → GBP 0.2137000 (markup included). The merchant is settled in SAR.

5. Scope

5.1 In scope

  • Any AED order paid on Geidea HPP: orders created by API (Create Session), by an SDK that shows Geidea HPP, or by Pay-by-Link. Includes saved-card payments that the customer starts on HPP.
  • Card payments, including Apple Pay, Google Pay and Samsung Pay.
  • Sale (paymentOperation = Pay). Full refund and partial refunds, including several partial refunds on one transaction.
  • UAE merchants on Geidea’s ecommerce gateway, on MPGS and CyberSource.
  • Order currency AED at launch. The solution supports other order currencies through configuration, with no code change.

5.2 Out of scope

  • Orders in another currency (merchants with ENABLE_MULTI_CURRENCY). They are processed as today, without MCP.
  • Tabby, Tamara and other alternative payment methods. HPP shows “Available in AED only” under them.
  • Flows with no HPP: Direct API where the merchant collects the card details, recurring and merchant-initiated payments.
  • Authorization and capture (PreAuthorize), including partial captures.
  • Merchant rebate on the markup.
  • VPN and proxy users. A wrong location is an accepted risk.

5.3 Phase 2

  • Zero and three-decimal currencies (JPY, KWD, BHD, OMR). They need PGW changes to amount handling, display, rounding and refunds, and enablement on APEX, Postilion and Planet. Their country mappings (JP, KW, BH, OM) stay inactive in MVP. Every interface format in MVP states the number of decimals, so Phase 2 needs no format change.

6. Solution approach

6.1 How it works

End-to-end view
  1. Planet publishes a daily rate file over SFTP. The rates include the markup. PGW loads, checks and caches the file.
  2. The merchant creates an AED order. The customer opens HPP.
  3. PGW looks up the customer’s IP in the MaxMind GeoIP2 database that PGW holds, and gets the country. PGW maps the country to a currency.
  4. If MCP is on for the merchant and the merchant offers that currency, PGW takes the rate from the cached file and shows the converted amount. The rates are fixed for the payment session.
  5. The customer pays. PGW authorizes in the chosen currency through MPGS or CyberSource and stores the rate on the transaction.
  6. PGW federates the transaction to APEX with the AED order amount in the main fields and the transaction amount, currency and rate in the new cardholder fields (section 8.3).
  7. The scheme file reaches Postilion in the transaction currency. Postilion clears in that currency. PGW’s enrichment file gives Postilion the AED view, so the PTLF to APEX matches the federation (section 8.4).
  8. APEX prices and pays out the merchant from the AED amount, as today.
  9. APEX includes the MCP transactions in the Daily Transaction File (DTF) to Planet, as for DCC. Planet accounts for the markup (section 8.5).
  10. A refund is made in AED by the merchant. PGW converts it at the rate stored on the original transaction.

6.3 Design principles

  • The merchant world stays in AED. No merchant-facing output carries the transaction currency, the rate or an MCP flag.
  • One conversion, at PGW. PGW converts once and stores the result. No downstream system recalculates an amount.
  • Location decides the offer. MCP is offered only when the customer’s location gives a currency the merchant offers. The customer can then switch between the offered currencies and AED.
  • Rates come from a cached file. No rate is fetched during a payment session.
  • Refunds use the original rate. Never a newer rate.

7. Scheme position and known risks

  • Outside DCC. Visa’s DCC rules apply when the currency is derived from the card (BIN). In MCP the currency comes from the customer’s IP location, the AED amount is shown next to it, and the customer can switch back to AED. The scheme clears in the currency the customer chose. Planet processes and reports these transactions as MCP (DTF Product Indicator 2, “Shop in Your Currency”), separate from DCC.
  • Double markup (accepted). A customer whose card is in AED may be shown a foreign currency while abroad. Both amounts are shown and the customer can switch to AED. No further disclosure is shown.
  • No rounding drift. Amounts are stored once by PGW and copied downstream.
  • Rate file availability. When no valid rate file is cached, MCP is suspended and HPP shows AED only (section 8.1).

For Risk & Compliance to assess: the IP-based offer as outside DCC obligations; the HPP display (section 8.1, HPP).

8. Requirements

8.1 PGW: PGW engineering team

HPP simulatorEnd-to-end view

Build-level detail is in the PGW dev stories S1 to S7.

Merchant configuration (S1)

Setting Level Purpose
MCP toggle in PGW Configuration (name to be set by PGW, for example ENABLE_DYNAMIC_MCP) Per MID, Live and Test Turns MCP on for the merchant
MCP currencies Per MID The transaction currencies the merchant offers, chosen from the MCP currency list
MCP currency list System Currencies MCP can offer. A currency is listed only if APEX supports it and Planet’s rate file carries it. 2-decimal currencies only in MVP. Set before go-live: see below.
Country-to-currency map System ISO country code → currency (GB → GBP, FR → EUR…). Phase 2 countries inactive.
MCP order currencies System Order currencies MCP applies to. AED at launch.
  • The MCP toggle must have a name that is clearly different from ENABLE_MULTI_CURRENCY and ENABLE_MULTI_CURRENCY_SETTLEMENT, which mean other things.
  • No markup is set in PGW. Markup is held at Planet and is included in the rates.
  • MCP currency list at go-live. Before production, Product gets the latest list of currencies APEX supports, agrees the list with Business and Commercial, and asks the PGW team to configure it. The list is configuration, so later changes need no code change.
  • The PGW integration team switches MCP on only after Operations confirms the merchant is registered with Planet for MCP (section 8.6).

Rate file (S2) - Fetch Planet’s daily rate file over SFTP, decrypt it (if Planet confirms PGP encryption, with Geidea’s private key; Planet holds the public key), parse it and store the rates in a PGW table. Layout: Planet MAS template 194 (Visa and Mastercard sections). Until the SFTP feed is live, load Planet’s sample file. - Basic checks only: header and trailer present, record count matches, file not loaded before. Planet guarantees its rates. A file that fails is not loaded, and Operations is alerted. - Quote from the Visa section. Rate direction: units of transaction currency for 1 unit of order currency (AED → GBP 0.2137000). Converted amount = order amount × rate. - Each rate has a validity window (48 hours in Planet’s sample, so daily files overlap). Use the rate from the latest loaded file that is valid at the time of the quote (S4). - If no valid rate exists for a currency, that currency is not offered. If no rate is valid at all, MCP is suspended for all merchants and Operations is alerted (S4).

Geolocation (S3) - Fetch the MaxMind GeoIP2 database (CSV) when MaxMind publishes a new release, parse it and store IP networks with their country in a PGW table. - Look up the customer’s IP address in this table before HPP shows the amount (S4). No external call during the session. - No country found: no MCP for the session. The payment is a regular AED payment.

HPP (S4) - MCP is offered only when all of these are true: the order currency is an MCP order currency (AED), paymentOperation = Pay, the MCP toggle is on, a valid rate file is cached, the IP gives a country, the country maps to an active currency, the merchant offers that currency, and the file has a valid rate for it. - Then HPP shows: the total in the proposed currency, the order amount in AED and the rate (“1 AED = 0.2137 GBP”), and a currency selector. The selector lists AED and every currency the merchant offers that has a valid rate. - When MCP is not offered, HPP shows AED only, with no selector. A customer in the UAE gets no selector. - The rates are taken once when HPP first loads and are fixed for the session. Switching currency re-prices from these rates. - The converted amount is rounded up to the currency’s minor unit. Example: AED 99.99 × 0.2137000 = GBP 21.367863 → GBP 21.37. - The selector and the amounts are shown above the wallet buttons. Wallet buttons use the currency and amount on screen. - Tabby and Tamara are available only when the selected currency is AED, with “Available in AED only” under them. - The confirmation shows the amount paid and the AED order amount, for example “GBP 21.37 (AED 100.00)”. The same applies to the email receipt that PGW sends for a Pay-by-Link payment when the customer has an email address.

Payment and the transaction record (S5) - Authorize in the chosen currency through MPGS or CyberSource. - Keep the order currency and amount and the transaction currency and amount as separate fields. - New fields on each transaction (purchase and refund): mcpBaseAmount and mcpBaseCurrency (the AED amount of this transaction), the MCP flag (true only when a conversion was applied), the rate, and the rate’s source (file and rate ID). - New field on the order: MCP offered flag (Y when HPP proposed a converted currency). Internal to PGW, kept for later conversion-rate tracking. Building that tracking is not part of this project. - Order totals (paid, refunded, remaining) are computed from mcpBaseAmount, never by adding amounts in different currencies. - Wallets: the amount and currency in the wallet token must equal the quote on HPP. If not, PGW rejects the payment.

Refunds (S6) - The merchant refunds in AED. For an MCP transaction PGW converts the refund at the rate stored on the original transaction and refunds in the transaction currency. - A non-final refund is converted and rounded down to the minor unit. The refund that brings the AED refunds to the full amount is set to: original transaction amount minus all earlier refunds in the transaction currency (last-cent rule). - The existing minimum refund amount (0.10) applies. No MCP-specific minimum is needed: AED 0.10 converts to at least one minor unit in every MVP currency.

Refund (AED) × 0.2137000 Refund (GBP) Rule
60.00 12.822000 12.82 Rounded down
40.00 (final) — 8.55 21.37 − 12.82
100.00 21.37 Equals the original

Second example: refunds of AED 33.33, 33.33 and 33.34 give GBP 7.12, 7.12 and 7.13 (total 21.37). Converting each one would give 7.12 + 7.12 + 7.12 = 21.36.

Merchant-facing outputs (S7) - In the callback (webhook), order inquiry, pay and refund responses, and Pay-by-Link inquiry, transaction.amount and transaction.currency of an MCP transaction carry the AED values. The rate, the MCP flag and the MCP offered flag are not returned. There is no setting to return them.

Federation and enrichment (S8, S9): see sections 8.3 and 8.4.

Required outcomes - The same fields come from the PGW federation and from the Postilion PTLF, so the two records match. - Refunds carry the same fields: the refund’s converted amount and the original rate. - Chargebacks arrive in the transaction currency. APEX matches them to the original by transaction reference (ARN or RRN), not by amount and currency, and uses the cardholder fields to apply them in AED. Partial chargebacks must never total more than the original AED amount. - A transaction flagged MCP in the PGW federation whose PTLF row does not carry the MCP fields, or the reverse, goes to an exception visible to Operations daily. - Merchant pricing, payout, refunds, merchant APIs and the Merchant Portal continue on the AED fields with no change. - DTF to Planet. APEX produces the DTF, as for DCC. MCP transactions (purchases and refunds) are included with field 22 Product Indicator = 2 and field 20 = the applied rate as a decimal, subject to Planet’s confirmation (section 8.5).

Required to be confirmed - Field keys for the API and the PTLF; currency format (alpha GBP or numeric 826); amount format and decimals; rate decimals (Planet uses 7); value of the identifier for non-MCP transactions. - Rounding for partial chargebacks (AED = transaction amount ÷ rate). - Exception handling for MCP mismatches.

8.4 Postilion: Musaad Haider — parked

The enrichment file format and its data set are being finalized. The PGW enrichment story (S9) waits on this.

Required outcomes - Clearing is unchanged: Postilion receives the DCF/TC33 in the transaction currency and clears in it. - For each MCP leg (purchase, refund, partial refund), PGW sends an enrichment record. Approach under discussion: reuse Postilion’s existing enrichment-file processing for PayGlocal transactions, with PGW supplying (a) the matching key (PGW order ID, RRN, authorization code), (b) the order view (AED amount and currency) and the transaction view (amount and currency), (c) the rate and the MCP flag. - Postilion builds the PTLF row for APEX with the order view in amount/transactionCurrency and the transaction view and rate in the new cardholder fields, copied with no recalculation. - Non-MCP ecommerce, POS, and POS DCC with Planet are unchanged.

Required to be confirmed - The enrichment layout (columns, positions, decimals), and that MCP records are processed before the matching DCF/TC33. - Matching on PGW order ID + RRN + authorization code for MPGS-routed transactions as well as CyberSource.

9. End-to-end flow

End-to-end view: purchase and refunds
Daily
  Planet  -> PGW       Rate file (template 194, markup included). PGW checks and caches it.

Purchase: order AED 100.00, customer in the UK pays GBP 21.37, merchant settled in SAR
  Merchant -> PGW      Create Session, AED 100.00
  Customer -> HPP      Opens the payment page
  PGW                  IP -> MaxMind -> GB -> GBP; GBP on for the merchant; rate 0.2137000 (Visa section)
  HPP -> Customer      GBP 21.37, AED 100.00, 1 AED = 0.2137 GBP, currency selector
  Customer -> HPP      Pays in GBP (card or wallet)
  PGW -> MPGS/CYBS     Authorize GBP 21.37 -> approved
  PGW -> Merchant      Callback: AED 100.00
  PGW -> APEX          Federation: AED 100.00 in main fields; GBP 21.37, rate, MCP flag in cardholder fields
  PGW -> Postilion     Enrichment record (day end)
  Scheme -> Postilion  DCF/TC33 in GBP 21.37; Postilion clears in GBP
  Postilion -> APEX    PTLF: same convention as the federation
  APEX                 Prices on AED 100.00, pays the merchant in SAR
  APEX -> Planet       DTF with the MCP row (Product Indicator 2)

Refund: merchant refunds AED 60.00, then AED 40.00
  Merchant -> PGW      Refund AED 60.00 -> PGW refunds GBP 12.82 (stored rate, rounded down)
  Merchant -> PGW      Refund AED 40.00 -> PGW refunds GBP 8.55 (last-cent rule)
  PGW -> APEX          Each refund federated in AED, with its GBP amount and the original rate
